# 变更管理 SOP

## 何时使用

触发场景（满足任一即调用）：
- 准备进行生产环境任何变更（代码/配置/架构）
- 关键词：「上线」「变更」「发布」「部署」「改配置」「升级」「迁移」「打补丁」
- 涉及多个团队或核心系统的调整

> **此 SOP 是强约束**，所有生产变更必须按此执行。dev/test 环境可简化。

---

## 核心原则

1. **可回滚** —— 没有回滚方案的变更不允许上线
2. **可灰度** —— 先小流量验证，再全量
3. **可追溯** —— 变更内容、时间、负责人、操作人全部留痕
4. **可观测** —— 变更前后关键指标必须可对比
5. **最小影响** —— 选择业务低峰期，避免大变更叠加

---

## 六步流程

### 第一步：变更申请（**发起人**）

> **目标**：把变更讲清楚，让审批人能判断

填写《变更申请单》（见 references/change-request-template.md），核心字段：

| 字段 | 说明 |
|---|---|
| **变更标题** | 一句话说清做什么 |
| **变更类型** | 代码 / 配置 / 数据库 / 网络 / 安全 |
| **变更等级** | P0（紧急）/ P1（重大）/ P2（一般）/ P3（低风险） |
| **变更原因** | 为什么做（背景、痛点） |
| **变更内容** | 具体改什么（PR/脚本/配置） |
| **影响范围** | 影响哪些服务、用户、数据 |
| **变更时间窗** | 计划开始/结束时间 |
| **回滚方案** | 怎么回退到变更前 |
| **验证标准** | 怎么确认成功 |
| **风险评估** | 可能出什么问题、应对 |

**自检清单**：
- [ ] 变更内容已自测通过
- [ ] 回滚方案已演练
- [ ] 已通知相关方（业务、客服、其他技术团队）
- [ ] 已确认无大变更冲突（同一时段无其他变更）

### 第二步：变更评估（**评估人**）

> **目标**：识别风险，确保方案可行

评估维度：

| 维度 | 关注点 |
|---|---|
| **技术可行性** | 方案是否正确？依赖是否就绪？ |
| **业务影响** | 影响多大？能否降级？ |
| **数据安全** | 是否有数据丢失/损坏风险？ |
| **回滚可靠性** | 回滚是否经过演练？耗时多长？ |
| **可观测性** | 监控告警是否覆盖？ |
| **兼容性** | 是否影响上下游、API、客户端？ |
| **合规性** | 是否符合安全/审计/合规要求？ |

**评估结论**：
- ✅ 通过：进入审批
- ⚠️ 需补充：退回补充材料
- ❌ 不通过：给出理由，必要时换方案

### 第三步：变更审批（**审批人**）

> **目标**：决策是否执行

| 等级 | 审批人 | 审批形式 |
|---|---|---|
| **P0 紧急** | 技术总监 + 业务负责人 | 即时会议 + 工单确认 |
| **P1 重大** | 技术负责人 + 业务接口人 | 邮件/工单确认 |
| **P2 一般** | Team Lead | 工单确认 |
| **P3 低风险** | 执行人自审 | 工单备注即可 |

**审批关注**：
- 业务影响是否可接受
- 时间窗口是否合理（业务低峰期）
- 回滚方案是否具体
- 应急联系人是否就位

**审批结果**：
- ✅ 通过：进入变更窗口
- ❌ 拒绝：说明理由，可重新申请

### 第四步：变更执行（**执行人**）

> **目标**：按计划执行，记录操作

#### 执行规范

1. **变更前**（变更开始前 30 分钟）
   - [ ] 通知相关方（IM 群、电话、邮件）
   - [ ] 确认监控告警已配置
   - [ ] 备份关键数据（DB、配置）
   - [ ] 准备回滚脚本（开新终端放好）

2. **变更中**
   - [ ] 按既定顺序执行
   - [ ] 每步记录命令、输出、时间
   - [ ] 监控关键指标（错误率、延迟、QPS）
   - [ ] 出现问题立即评估是否回滚

3. **变更后**
   - [ ] 立即验证（5-15 分钟）
   - [ ] 通知相关方变更完成
   - [ ] 持续监控（1-24 小时）

#### 灰度策略

\`\`\`
单实例验证
    ↓
10% 流量灰度（5-15 分钟观察）
    ↓
50% 流量灰度（10-30 分钟观察）
    ↓
100% 全量（持续监控 1-24 小时）
\`\`\`

**灰度决策点**（每一步都要看）：
- 错误率无变化 → 继续
- 错误率轻微上升 → 观察 5 分钟
- 错误率显著上升 → 立即回滚

### 第五步：变更验证（**执行人 + 业务方**）

> **目标**：确认变更成功，未引入新问题

#### 验证清单

- [ ] **核心功能**：业务方验证关键路径
- [ ] **监控指标**：错误率/延迟/吞吐量正常
- [ ] **日志检查**：无新报错/异常
- [ ] **依赖检查**：上下游服务正常
- [ ] **用户体验**：抽样验证用户视角
- [ ] **数据一致性**：抽样核对数据准确

#### 观察期

| 等级 | 强制观察期 |
|---|---|
| P0 | 24 小时 |
| P1 | 4 小时 |
| P2 | 1 小时 |
| P3 | 30 分钟 |

**观察期内异常**：
- 立即评估是否需要回滚
- 不要尝试「再改一次修一下」，先回滚再说

### 第六步：变更归档（**执行人**）

> **目标**：形成可追溯的记录，便于复盘和审计

归档内容：

\`\`\`bash
# 1. 变更工单填写
- 实际开始时间 / 结束时间
- 执行人 / 操作命令
- 验证结果 / 监控截图
- 是否成功 / 是否回滚 / 备注

# 2. 文档更新
- Runbook 更新（如有变更涉及）
- Wiki 同步（如有架构变更）
- FAQ 补充（如有用户侧变化）

# 3. 复盘（如有问题）
- 问题根因
- 处理过程
- 改进措施
\`\`\`

## 变更等级与时间窗

### P0 紧急变更

- **场景**：安全漏洞、生产严重故障、性能严重恶化
- **审批**：技术总监 + 业务负责人
- **时间窗**：立即（24 小时）
- **回滚 SLA**：5 分钟内

### P1 重大变更

- **场景**：核心功能上线、架构调整、数据库迁移
- **审批**：技术负责人 + 业务接口人
- **时间窗**：业务低峰期（如凌晨 0-6 点）
- **回滚 SLA**：15 分钟内

### P2 一般变更

- **场景**：非核心功能、配置调整、依赖升级
- **审批**：Team Lead
- **时间窗**：工作时间或业务低峰
- **回滚 SLA**：30 分钟内

### P3 低风险变更

- **场景**：文案调整、日志配置、监控规则
- **审批**：自审
- **时间窗**：任意
- **回滚 SLA**：1 小时内

## 应急场景

### 变更中出现故障

\`\`\`
立即评估 → 决定是否回滚
    ↓
是                否
回滚 ↓           继续修复
执行回滚 ↓       → 修复成功 → 验证 → 归档
通知相关方 ↓                  ↓
回滚失败 ↓                修复失败 → 回滚
启动故障应急流程
\`\`\`

**核心原则**：**回滚永远比修复快**，所以拿不准就回滚。

### 变更后才发现问题

- 立即评估影响范围
- 是严重问题 → 启动回滚 + 故障应急
- 是轻微问题 → 可观察中修复，但要立即通知

## 禁止事项

| 红线 | 说明 |
|---|---|
| ❌ 无变更申请直接操作 | 必须走流程 |
| ❌ 无回滚方案的变更 | 不允许执行 |
| ❌ 跳过灰度直接全量 | P1+ 必须灰度 |
| ❌ 同一时段多个大变更 | 避免叠加风险 |
| ❌ 业务高峰期变更 P1 | 必须选择低峰期 |
| ❌ 变更中未通知相关方 | 群消息 + 工单确认 |
| ❌ 无验证直接归档 | 必须确认成功 |
| ❌ 私自回滚不记录 | 所有操作必须留痕 |
