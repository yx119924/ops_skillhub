# 故障排查通用框架

## 何时使用

触发场景（**任意**告警、故障、服务异常时都应先调用）：
- 收到任何监控告警（CPU/内存/磁盘/网络/服务不可用）
- 用户报告服务异常、慢、报错
- 关键词：「服务挂了」「页面打不开」「503」「502」「500」「异常」「告警」「故障」「事故」
- **不适用场景**：SSH 连不上、磁盘满、CPU 高这类已有专用 skill 的场景

> 这是**总框架**，遇到具体场景应该叠加对应专项 skill（ops-disk-cleanup / ops-high-cpu-load / ops-ssh-troubleshoot 等）。

---

## 核心心法

1. **先全局后细节** —— 不要一头扎进日志，先看监控大盘
2. **先止血后定位** —— 恢复服务优先于找根因
3. **先易后难** —— 重启 → 切流量 → 回滚，最后才深入代码
4. **先记录后操作** —— 时间线记录比记忆靠谱
5. **先沟通后独断** —— 影响业务时及时同步

---

## 五步排查框架

### 第一步：确认范围（**1-3 分钟**）

> **目标**：知道影响多大、有多紧急、是否需要立即响应

\`\`\`bash
# 1. 影响范围
- 是单个实例还是多个？
- 影响哪些业务/用户？
- 内部还是外部用户感知？

# 2. 紧急程度
- P0：核心业务完全不可用
- P1：核心业务部分受影响
- P2：非核心业务异常
- P3：内部工具/告警噪音

# 3. 持续时间
- 何时开始？监控告警时间
- 第一次发现？最后一次正常时间
\`\`\`

**关键判断**：
- P0 立即拉群 → 启动应急流程
- P1 短时间能恢复 → 5 分钟内处理
- P2/P3 排期处理

### 第二步：快速止血（**3-10 分钟**）

> **目标**：在 10 分钟内恢复服务，不求根因

#### 通用止血手段（按风险递增）

| 手段 | 操作 | 风险 | 适用 |
|---|---|---|---|
| **重启服务** | `systemctl restart xxx` | 中（可能丢未保存状态） | 任何服务 |
| **重启实例** | 云控制台/CLI 重启 | 中 | 单实例故障 |
| **切流量** | LB 摘掉异常节点 | 低 | 多实例部署 |
| **回滚版本** | 部署上一稳定版本 | 中（配置可能漂移） | 升级后故障 |
| **扩容** | 加实例/加资源 | 低 | 容量不足 |
| **限流/降级** | 临时关闭非核心功能 | 中（影响体验） | 过载场景 |
| **回切 DNS** | 切回旧 IP | 低 | 解析层故障 |
| **关闭告警** | ack 防止打扰 | 低 | 仅 P2+ |

**核心原则**：
- ⚠️ 止血 ≠ 修复，先恢复服务
- ⚠️ 止血操作要记录（便于复盘）
- ⚠️ 涉及破坏性操作（kill -9、rm）必须二次确认

### 第三步：深入定位（**10-60 分钟**）

> **目标**：找到根因，但不要影响服务

#### 分层诊断（由外到内）

\`\`\`
用户层：能正常访问吗？报错什么？
        ↓
DNS/网络层：域名解析？路由？连通性？
        ↓
接入层（LB/WAF/CDN）：请求到了吗？健康检查？
        ↓
应用层（Web/API）：服务进程在跑吗？端口监听吗？
        ↓
运行时（JVM/容器）：内存？线程？GC？
        ↓
数据层（DB/Cache）：连接池？慢查询？主从延迟？
        ↓
系统层（OS）：CPU/内存/磁盘/网络？
        ↓
依赖层（上游服务）：第三方 API？DNS？
        ↓
物理层：机房？网络设备？硬件？
\`\`\`

#### 定位手段

| 层 | 工具 |
|---|---|
| 用户 | curl 模拟访问、浏览器 F12 |
| DNS | dig、nslookup、ping |
| 网络 | mtr、traceroute、tcpdump |
| 接入 | LB 控制台、WAF 日志、CDN 日志 |
| 应用 | journalctl、strace、jstack |
| 运行时 | jstat、jmap、cAdvisor |
| 数据 | DB 慢查询日志、连接池监控 |
| 系统 | top、iostat、vmstat、sar |
| 依赖 | 服务调用链 tracing |
| 物理 | IPMI、BMC、带外管理 |

### 第四步：修复验证（**5-30 分钟**）

> **目标**：真正解决问题，并确认没引入新问题

\`\`\`bash
# 1. 修复方案评估
- 是临时止血还是永久修复？
- 是否需要变更审批？
- 是否需要灰度？

# 2. 修复执行
- 在测试环境先验证
- 生产环境分批灰度
- 监控关键指标

# 3. 验证清单
- [ ] 监控指标恢复正常
- [ ] 业务功能验证通过
- [ ] 关联服务正常
- [ ] 日志无新报错
- [ ] 性能指标未恶化
\`\`\`

### 第五步：事后复盘（**24-48 小时内**）

> **目标**：不让同样的故障发生第二次

#### Postmortem 模板（见 references/postmortem-template.md）

必含内容：
1. **事故概要**：时间、影响、持续时间
2. **时间线**：每个关键节点
3. **根因**：直接原因 + 根本原因
4. **处理过程**：做对了什么、可以改进什么
5. **改进措施**：短期（1 周）+ 中期（1 月）+ 长期（季度）
6. **经验教训**：可复用的 SOP

#### 必做事项

- [ ] 写 Postmortem 文档
- [ ] 进 Issue Tracker 跟踪改进项
- [ ] 更新 Runbook / SOP
- [ ] 在团队周会分享
- [ ] 完善监控告警（避免漏报/误报）

## 故障沟通模板

### 拉群通知（事故开始）

\`\`\`
【P0 故障】2026-09-06 10:30
📍 影响：用户登录接口 5xx 率飙升
⏰ 开始：10:25 左右
👥 负责人：@xxx @yyy
📊 状态：正在止血
🔗 Dashboard：https://grafana.xxx/d/abc
\`\`\`

### 进度更新（每 15-30 分钟）

\`\`\`
【进展】10:50
✅ 已止血：重启异常实例 3 台
⏳ 持续观察：监控指标是否恢复
🎯 下一步：定位根因 + 修复
\`\`\`

### 恢复通知（事故结束）

\`\`\`
【恢复】11:30
✅ 服务已恢复
📝 原因：xxx 实例 OOM 被杀，已临时扩容
📋 复盘文档：https://wiki.xxx/postmortem/2026-09-06
🛡 改进项：3 项（详见文档）
\`\`\`

## 输出格式

完整排查后给出：

1. **事故概要**：影响范围、持续时间、级别
2. **时间线**：关键节点记录
3. **根因**：直接 + 根本
4. **止血措施**：已执行的恢复操作
5. **后续动作**：复盘文档链接、改进项跟踪

## 反模式（不要这么做）

| ❌ 反模式 | ✅ 正确做法 |
|---|---|
| 不确认范围就埋头排查 | 先 1 分钟确认影响范围 |
| 根因没找到就强切版本 | 至少先止血再深挖 |
| 不记录就开始操作 | 边干边记时间线 |
| 一人闷头排查 | 该拉群就拉群 |
| 修复完不验证 | 必须监控+业务双重验证 |
| 修复完不复盘 | 24 小时内 Postmortem |
| 把所有异常都当 bug | 区分 bug / 配置 / 容量 / 依赖 |
